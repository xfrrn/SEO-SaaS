`@app/auth-sdk/paypal` 提供服务端 PayPal Orders v2 客户端，配套 Next.js 示例实现一次性购买数字内容。它默认使用沙箱，通过标准 `fetch` 调用 PayPal，不需要安装额外支付 SDK。认证沿用 Better Auth；PayPal 支付不是登录插件，也不是自动续费订阅。

PayPal.cn 的[全球收单](https://www.paypal.cn/portal/merchant/online-checkout)使用 PayPal REST API。商户需要在 PayPal.cn 注册并开通相应服务，再取得所用应用的 API 凭据。能否开通、支持的地区和币种以商户账户实际能力为准。本站已有的 [PayPal 登录](/docs/authentication/paypal)只负责身份验证。

## 安装与配置

先按 [SDK 中文快速接入](/docs/guides/sdk-quickstart-zh)安装本地 SDK，接入邮箱密码认证和 PostgreSQL。基础示例位于 `packages/app-sdk/examples/nextjs/`。

将该目录下 `paypal/` **里面的内容**合并到项目根目录；使用 `src/` 布局时，将 `app/`、`lib/` 合并到 `src/`。保留基础示例的 `lib/auth.ts`、`lib/auth-client.ts`、`lib/database.ts` 和 `lib/env.ts`。已有 Stripe 配置可以保留，两种支付方式分别管理自己的权益。

模板使用 Better Auth 的 URL 工具，应用中直接安装对应版本的核心包：

```sh
pnpm add @better-auth/core@1.7.6
```

在服务端环境变量中填写：

```dotenv
PAYPAL_ENVIRONMENT=sandbox
PAYPAL_CLIENT_ID=
PAYPAL_CLIENT_SECRET=
PAYPAL_WEBHOOK_ID=
```

在 [PayPal Developer Dashboard](https://developer.paypal.com/dashboard/) 创建 Sandbox REST 应用，获取 Client ID 和 Secret。为同一应用配置 webhook，填写 HTTPS 地址 `https://你的域名/api/paypal/webhook`，将该 webhook 的 ID 填入 `PAYPAL_WEBHOOK_ID`。Webhook ID 不是 Client ID，也不是自己生成的签名密钥。所有变量只在服务端使用，不加 `NEXT_PUBLIC_` 前缀，不提交真实凭据。

订阅以下事件：

* `PAYMENT.CAPTURE.COMPLETED`
* `PAYMENT.CAPTURE.PENDING`
* `PAYMENT.CAPTURE.DENIED`
* `PAYMENT.CAPTURE.REFUNDED`
* `PAYMENT.CAPTURE.REVERSED`

本地调试需要将公开 HTTPS 地址转发到本机 `/api/paypal/webhook`。本例使用 PayPal 验签接口，需要真实沙箱交易触发的通知；Webhook Simulator 的模拟事件不能代替真实应用的验签测试。参阅[官方 webhook 验证说明](https://developer.paypal.com/api/rest/webhooks/rest/)。

## 创建支付表

先完成 Better Auth 用户表迁移，再用 PostgreSQL 客户端对同一个数据库执行 `paypal/migrations/001_paypal.sql`。例如在未移动模板文件时：

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f packages/app-sdk/examples/nextjs/paypal/migrations/001_paypal.sql
```

这里的路径相对于仓库根目录；复制到应用后按实际路径调整。SQL 创建 `paypal_payment` 与 `paypal_webhook_event`，用于记录归属、金额、PayPal 订单和收款 ID、状态及已处理事件。Better Auth CLI 不会创建这些业务表。若你修改了 Better Auth 用户表名或用户 ID 类型，需要相应调整 SQL 外键。

示例商品在 `paypal/lib/paypal.ts` 中设置为 `digital-access`，价格 `10.00 USD`，是演示价格。上线前改成你的实际商品和价格；已有订单保留创建时的金额快照。示例支付表使用两位小数，仅适合两位小数币种；切换 JPY 等币种时应同步调整表结构和金额逻辑。

## 付款与权限

登录后访问 `/paypal`，点击“前往 PayPal 付款”。在 PayPal 批准付款并返回后，点击“确认 / 刷新付款状态”。只有服务端核实收款完成后，`/api/paypal/access` 才允许访问。

| 路由                         | 用途                                  |
| -------------------------- | ----------------------------------- |
| `POST /api/paypal/orders`  | 验证会话、请求来源和商品价格，保存本地订单，再创建 PayPal 订单 |
| `POST /api/paypal/capture` | 验证订单属于当前用户，核对金额和币种，执行收款并更新状态        |
| `POST /api/paypal/webhook` | 验签后重新查询订单，事务中更新支付状态和事件记录            |
| `GET /api/paypal/access`   | 根据当前登录用户的已付款记录检查商品权限                |

前端只提交 `paymentId`，不会决定价格、币种或付款人。该 ID 是 UUID v4，客户端为同一付款保存重试键；服务端另行持久化 capture 请求键。发生网络或网关错误时使用同一个订单重试。PayPal 幂等键有保留期限，长期未完成且状态不明的订单应先在商户后台核对，再人工处理，不要无限重试或直接创建替代订单。

回跳 URL 中的 `payment`、PayPal `token`、页面提示和 `APPROVED` 状态都不能授予权益。订单及 capture 必须均为 `COMPLETED`，且归属、金额和币种匹配。`PENDING` 保持无权限；退款（包括部分退款）、撤销或拒付通知会移除此订单的权限。退款操作在 PayPal 商户后台执行，本例只处理其状态通知。

示例将权益直接表示为支付表中的 `paid` 状态，不会在每次通知时重复发放积分。若改成发积分、发邮件或开通外部资源，要把业务写入和事件去重放在同一事务中，外部副作用使用持久化任务。本示例在请求 PayPal 时持有订单行锁来串行处理同一订单，适合低吞吐量场景；高并发时改用持久化任务处理。

## 在其他框架中使用

客户端只依赖标准 Web API；Next.js 示例因使用 `pg` 而指定 Node.js runtime。其他运行时可以使用 SDK 客户端并接入自己的数据库与 HTTP 路由。

```ts
import { createPayPalClient } from "@app/auth-sdk/paypal";

const paypal = createPayPalClient({
  clientId: env.PAYPAL_CLIENT_ID,
  clientSecret: env.PAYPAL_CLIENT_SECRET,
  webhookId: env.PAYPAL_WEBHOOK_ID,
  environment: "sandbox",
});

// payment 必须是服务端创建并持久化、且属于当前用户的订单。
const order = await paypal.createOrder({
  requestId: payment.id,
  referenceId: payment.id,
  amount: { currency_code: payment.currency, value: payment.amount },
  returnURL: "https://example.com/paypal",
  cancelURL: "https://example.com/paypal",
});
```

还提供 `getOrder(orderId)`、`captureOrder({ orderId, requestId })` 和 `verifyWebhook({ headers, body })`。验签时传入请求正文文本和原始请求头；SDK 会调用 PayPal 的验签 API，仅接受 `SUCCESS`。签名或事件无效时抛出名称为 `PayPalWebhookError` 的错误，服务不可用时抛出普通错误，调用方应返回可重试响应。

SDK 不保存用户、订单或权限。创建订单与收款接口必须在服务器授权后调用，使用持久化的幂等键；客户端传入的金额和订单归属不可直接信任。只将 PayPal 返回且经过域名检查的批准链接交给浏览器，参照完整模板实现。

示例按 `PAYPAL_ENVIRONMENT` 隔离支付记录和权益，沙箱付款不会授予正式环境权限。部署时仍应为测试与生产使用各自的应用、数据库和 webhook 地址。

## 验证与上线

在仓库运行：

```sh
pnpm exec vitest run packages/app-sdk/test/paypal.test.ts packages/app-sdk/examples/nextjs/paypal.test.ts
pnpm --filter @app/auth-sdk typecheck:example
pnpm typecheck
```

自动化测试使用模拟 PayPal 响应，不会真实扣款。接入自己的 Sandbox 凭据和数据库后，还需使用独立沙箱买家账户完成付款、取消、待处理和退款验证，确认 webhook 送达以及 `/api/paypal/access` 的授权结果。最后才切换 `PAYPAL_ENVIRONMENT=live`，同时替换同一正式应用下的 Client ID、Secret 和 Webhook ID，并配置正式 HTTPS 地址与商品价格。

接口依据：[Orders v2](https://developer.paypal.com/api/orders/v2)、[Webhook 验签](https://developer.paypal.com/api/webhooks/v1/verify-webhook-signature-post)、[幂等请求](https://developer.paypal.com/api/rest/reference/idempotency/)。
